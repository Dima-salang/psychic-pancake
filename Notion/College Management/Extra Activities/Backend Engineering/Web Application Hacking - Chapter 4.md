## 🔷 PART 1: ENUMERATING CONTENT AND FUNCTIONALITY (Pages 74-93)

### 1.1 Web Spidering (Pages 74-77)

**What is Spidering?**

Spidering (or crawling) is the automated process of navigating through a web application by following links from a starting point, building a complete map of all reachable content. Think of it like a search engine bot indexing a website.

**How Spiders Work:**

A spider begins with a seed URL (typically the homepage), fetches the page, parses it for links, adds those links to a queue, and repeats the process until no new links are found. Modern spiders also execute JavaScript to capture dynamically generated content.

**Limitations of Automated Spidering:**

Spidering has significant blind spots that manual testing must cover. JavaScript-heavy applications often generate links dynamically that spiders miss. Links requiring specific user interactions like mouse clicks, form submissions, or authentication steps remain invisible to basic crawlers. Content hidden behind dropdown menus, tabs, or modal dialogs often stays undiscovered. Most critically, any content not linked from the crawlable surface—including backup files, test pages, administrative interfaces, and API endpoints—remains completely invisible to automated spidering.

**Spidering Configuration Best Practices:**

Configure your spider to use the application's authentication credentials to reach protected content. Set appropriate crawl depth limits to prevent infinite crawling of calendar widgets or paginated content. Configure the spider to submit forms with plausible test data to discover form-handling endpoints. Enable JavaScript execution for modern applications. Always compare spider results against manual browsing to identify gaps.

**Practical Spidering Tools:**

Burp Suite's spider offers excellent integration with its proxy and scanner. OWASP ZAP provides a powerful open-source alternative. For command-line use, wget with recursive options or specialized tools like Photon and Scrapy serve specific needs.

### 1.2 User-Directed Spidering (Pages 77-80)

**The Concept:**

Rather than relying solely on automated spidering, user-directed spidering combines human exploration with automated capture. You manually browse the application through an intercepting proxy while the tool records every request, building a comprehensive map based on actual usage patterns.

**Why This Approach Works:**

User-directed spidering discovers functionality that automated spiders miss because you naturally exercise complex workflows, trigger JavaScript events, and navigate authentication requirements. Your human judgment identifies interesting functionality worth investigating further. The approach also builds your mental model of how the application actually works.

**Implementation:**

Configure your browser to use Burp Suite or OWASP ZAP as a proxy. Ensure the proxy is intercepting and recording traffic. Browse the application systematically through every feature you can access. Review the site map generated by your proxy tool, identifying areas for deeper investigation.

### 1.3 Discovering Hidden Content (Pages 80-93)

**What is Hidden Content?**

Hidden content refers to any application functionality, pages, files, or directories that exist on the server but aren't linked from the visible application structure. This includes backup files, administrative interfaces, test pages, API endpoints, configuration files, and development artifacts.

**Why Hidden Content Exists:**

Developers often leave backup files during updates, create test pages that never get removed, deploy administrative interfaces without proper access controls, and fail to clean up configuration files or installation scripts. Third-party components bring their own administrative pages that administrators forget exist.

**Discovery Technique 1: Brute-Force Enumeration**

Brute-force enumeration systematically guesses common paths and filenames using wordlists. The approach requires identifying likely naming patterns and testing variations systematically.

Common targets include administrative paths like /admin, /administrator, /manage, /console, and /backend. Configuration files such as web.config, .htaccess, config.php, and database.yml often expose sensitive information. Backup files frequently use patterns like index.php.bak, index.php~, index.old, and Copy of index.php. Development artifacts including test.php, debug.php, log.txt, and .git directories reveal implementation details.

Effective wordlists combine common directory names, technology-specific paths, and application-specific terms derived from visible content. Start with small, targeted wordlists before running extensive brute-force attacks that generate noise and may trigger rate limiting.

**Discovery Technique 2: Inference from Visible Content**

Analyze visible content to predict hidden structure. URL patterns in visible areas often reflect the complete application architecture. Comments in HTML, JavaScript, and CSS frequently reference unpublished functionality. JavaScript files contain hardcoded API endpoints and internal paths. Error messages reveal framework, language, or database details that suggest specific paths to test.

When you observe /products/view?id=1, immediately test /products/edit, /products/delete, /products/admin, and /api/products. If the application uses WordPress, test /wp-admin, /wp-content/plugins, and /wp-json/wp/v2/users.

**Discovery Technique 3: Public Information Sources**

Information outside the application itself often reveals hidden functionality. Robots.txt files explicitly list paths the site owner wants hidden from search engines. Sitemap.xml files sometimes include unlinked pages. Search engine caches and archives like the Wayback Machine preserve previously accessible content. GitHub repositories, documentation, and support forums leak implementation details. WHOIS records and DNS data reveal infrastructure information.

**Discovery Technique 4: Leveraging Common Defaults**

Every framework, CMS, and server technology has default paths that administrators often fail to change. Knowing these defaults provides immediate testing targets.

| Technology | Default Administrative Paths |
|-----------|------------------------------|
| WordPress | /wp-admin, /wp-login.php, /wp-json/ |
| Joomla | /administrator, /administrator/index.php |
| Drupal | /user, /admin, /node/add |
| Apache Tomcat | /manager/html, /host-manager/html |
| Jenkins | /jenkins, /login |
| phpMyAdmin | /phpmyadmin, /pma, /myadmin |
| AWS S3 | Common bucket naming patterns |

### 1.4 Application Pages Versus Functional Paths (Pages 93-96)

**Understanding the Distinction:**

Modern web applications blur the line between discrete pages and functional endpoints. Traditional applications use distinct URLs for each page. Modern single-page applications (SPAs) and API-driven applications use JavaScript to modify a single page while communicating with backend endpoints.

**Implications for Mapping:**

You must identify both visible page structures and underlying API endpoints. A single visible page might generate dozens of API calls. Functional paths often follow REST conventions where the URL identifies a resource and the HTTP method specifies the operation.

**Analyzing Functional Paths:**

When you see /api/users/123 with GET requests, immediately test the same endpoint with POST, PUT, DELETE, and PATCH methods. Check for /api/users (list all users), /api/users/123/profile, /api/users/123/permissions, and /api/admin/users. Parameter-based functionality like /page.php?view=profile suggests alternative view values including admin, config, debug, and source.

### 1.5 Discovering Hidden Parameters (Pages 96-97)

**What Are Hidden Parameters?**

Hidden parameters are request parameters that the application accepts and processes but doesn't explicitly include in visible forms or links. They often enable debugging features, administrative functions, or alternative code paths that developers intended to keep secret.

**Discovery Techniques:**

Parameter guessing involves adding common parameter names to existing requests. When requesting /search?q=test, try adding &debug=1, &admin=true, &source=yes, &format=json, or &env=dev.

Observing application behavior reveals parameter processing. Error messages mentioning unexpected parameters, changes in response size or timing, and differences in HTML structure all suggest parameter recognition.

Back-end source analysis through exposed .git directories, backup files, or error stack traces reveals the complete parameter set that the application accepts.

## 🔷 PART 2: ANALYZING THE APPLICATION (Pages 97-114)

### 2.1 Identifying Entry Points for User Input (Pages 98-101)

**What Constitutes an Entry Point?**

Every location where user-supplied data enters the application represents a potential entry point for attacks. Comprehensive mapping must identify every possible input vector.

**URL Entry Points:**

Query string parameters in GET requests represent the most obvious entry points. Path parameters in REST-style URLs like /users/123 where 123 is user-controlled provide injection opportunities. Fragment identifiers (the portion after #) sometimes get processed by JavaScript and sent to servers.

**Request Body Entry Points:**

POST request bodies contain form data, JSON payloads, XML documents, and file uploads. Content-Type headers determine how the server parses body content, creating opportunities for content-type confusion attacks.

**Header Entry Points:**

Cookies store session identifiers and preferences that applications process. User-Agent strings sometimes get logged to databases or displayed in administrative interfaces. Referer headers might be stored or processed. Custom headers including X-Forwarded-For, X-Requested-With, and application-specific headers all represent input vectors.

**Out-of-Band Entry Points:**

Webhooks receive data from external services. Email processing systems parse incoming messages. File imports including CSV, XML, and image processing accept external data. Third-party API integrations introduce external input.

**Practical Identification:**

Review your proxy history for every request generated during browsing. Extract all parameters, headers, and body content. Test each identified entry point with distinctive values to confirm server-side processing. Document whether the input appears in responses (potential XSS), gets stored (potential stored XSS), or affects application logic (potential injection).

### 2.2 Identifying Server-Side Technologies (Pages 101-107)

**Why Technology Fingerprinting Matters:**

Knowing the server-side technology stack guides your vulnerability research. Specific frameworks have known vulnerabilities, default configurations, and characteristic behavior patterns. Technology identification focuses your testing on relevant attack vectors.

**Fingerprinting Methods:**

Banner grabbing examines Server headers, X-Powered-By headers, and custom headers that reveal technology choices. Cookie names provide strong indicators—PHPSESSID indicates PHP, JSESSIONID suggests Java, ASP.NET_SessionId reveals ASP.NET, and connect.sid indicates Node.js/Express.

URL structures and file extensions reveal technology choices. .php files suggest PHP, .jsp and .do indicate Java, .aspx reveals ASP.NET, and Rails-style routes without extensions suggest Ruby on Rails.

Behavioral analysis observes how the application responds to specific inputs. Error messages often include stack traces with framework names. Request handling differences including parameter parsing, URL normalization, and response formatting reveal underlying technologies.

**Comprehensive Fingerprinting Checklist:**

Request non-existent pages to trigger error messages that reveal stack traces and framework details. Send malformed requests that different technologies handle differently. Analyze session token formats and cookie structures. Review JavaScript files for framework-specific code patterns. Check for framework-specific paths and default files.

---

### 2.3 Identifying Server-Side Functionality (Pages 107-111)

**Mapping Application Logic:**

Beyond identifying technologies, you must understand what the application actually does. This requires analyzing the business logic, workflow patterns, and data relationships.

**Functional Analysis Approach:**

Document every user action and its corresponding server request. Identify multi-step processes including registration, checkout, password reset, and content creation. Map state transitions and decision points. Look for privilege differentiation between user types.

**Data Relationship Mapping:**

Identify how data objects relate to each other. User profiles connect to posts, comments, messages, and settings. Financial applications link accounts, transactions, beneficiaries, and limits. Understanding these relationships reveals horizontal privilege escalation opportunities where you might access other users' related data.

**Workflow State Analysis:**

Complex workflows often maintain state that can be manipulated. Check whether you can skip steps, repeat steps, or access steps out of order. Test whether completing a workflow and then revisiting intermediate steps reveals new options or bypasses restrictions.

### 2.4 Mapping the Attack Surface (Pages 111-114)

**Synthesizing Your Findings:**

Attack surface mapping combines all gathered information into a comprehensive view of viable attack vectors. This living document guides your subsequent testing phases.

**Attack Surface Components:**

Authentication mechanisms including login, registration, password reset, and account recovery represent high-value targets. Session management endpoints handling token generation, validation, and termination require scrutiny. Access control enforcement points at every functionality boundary need testing. Input handling across all identified entry points demands injection testing. Business logic workflows contain state manipulation opportunities.

**Prioritization Framework:**

Prioritize testing based on several factors. High-impact functionality including financial transactions, administrative actions, and sensitive data access deserves immediate attention. High-likelihood targets based on technology vulnerabilities and common misconfigurations offer efficient testing opportunities. Low-hanging fruit like obvious injection points and missing access controls provide quick wins.

**Documentation Standards:**

Maintain detailed records of every discovered endpoint including URL, HTTP methods accepted, parameters required, authentication requirements, and observed behavior. Note technology indicators and their confidence levels. Document relationships between endpoints and workflow sequences. Record all test inputs and application responses for later analysis.

## 🔷 PART 3: ADVANCED MAPPING TECHNIQUES

### 3.1 Handling Modern Application Architectures

**Single-Page Applications (SPAs):**

SPAs load a single HTML page and dynamically update content via JavaScript API calls. Traditional spidering fails because links don't trigger full page loads. Mapping requires monitoring network traffic for API calls, analyzing JavaScript bundles for endpoint definitions, and using browser automation tools that execute JavaScript properly.

**API-First Applications:**

Modern applications often expose comprehensive APIs that web interfaces only partially utilize. Map the complete API surface including undocumented endpoints by analyzing mobile application traffic, examining JavaScript code for all API calls, and testing common API patterns beyond those visibly used.

**Microservices Architectures:**

Distributed applications split functionality across multiple services. Mapping must identify service boundaries, inter-service communication patterns, and potential inconsistencies in security enforcement between services. Look for internal API calls that might be reachable externally and service discovery endpoints that reveal infrastructure details.

### 3.2 Authentication and Session Contexts

**Privilege-Based Mapping:**

Applications present different functionality based on user privileges. Comprehensive mapping requires examining the application from multiple perspectives: unauthenticated users, standard authenticated users, and users with various privilege levels including administrative access.

**Account Provisioning Strategies:**

When testing requires multiple account types, determine how to obtain them. Self-registration might be available. Administrative interfaces might allow account creation. Account invitation features could be exploitable. In some cases, you must request additional test accounts from the client.

### 3.3 Handling Application State

**Stateful Analysis:**

Applications maintain server-side state that affects available functionality. Document how state changes: session variables, database records, file system contents, and cache entries. Identify state-dependent behavior where the same request produces different results based on previous actions.

**Race Condition Opportunities:**

State manipulation creates race condition vulnerabilities where simultaneous requests produce unexpected results. Look for scenarios where checking a condition and acting upon it are separate operations that might be interrupted.

## 🔷 PART 4: TOOLS AND AUTOMATION

### 4.1 Proxy-Based Tools

**Burp Suite:**

Burp Suite's site map automatically organizes discovered content hierarchically. The target analyzer identifies entry points and parameters. Content discovery runs automated brute-force enumeration. The sequencer analyzes session token randomness.

**OWASP ZAP:**

ZAP offers similar functionality with strong open-source automation. The AJAX spider handles JavaScript-heavy applications. Forced browsing performs hidden content discovery. The fuzzer supports automated parameter testing.

### 4.2 Specialized Discovery Tools

**Content Discovery:**

Dirb and Gobuster perform fast directory and file brute-forcing. Feroxbuster offers recursive discovery with intelligent filtering. FFUF provides flexible fuzzing with extensive customization. Each tool accepts wordlists and generates requests efficiently.

**Technology Identification:**

Wappalyzer browser extensions identify technologies in real-time. BuiltWith provides detailed technology profiles. WhatWeb offers command-line fingerprinting. These tools combine multiple identification methods for comprehensive results.

## 🔷 PART 5: METHODOLOGY AND WORKFLOW

### 5.1 Systematic Mapping Process

**Phase 1: Initial Reconnaissance**

Begin with passive information gathering without direct interaction. Collect domain and infrastructure information. Review public sources for leaked information. Identify hosting providers and CDN usage.

**Phase 2: Automated Spidering**

Configure spidering tools with appropriate scope and authentication. Run multiple spider passes with different configurations. Compare results and identify gaps requiring manual coverage.

**Phase 3: Manual Exploration**

Browse the application systematically through an intercepting proxy. Exercise all visible functionality completely. Document multi-step workflows and state-dependent behavior. Note areas where automated spidering failed.

**Phase 4: Hidden Content Discovery**

Run targeted brute-force enumeration based on technology identification. Analyze discovered content for additional clues. Iterate discovery based on findings.

**Phase 5: Technology Fingerprinting**

Confirm technology stack through multiple methods. Research known vulnerabilities and default configurations. Identify framework-specific testing approaches.

**Phase 6: Attack Surface Documentation**

Synthesize all findings into comprehensive documentation. Prioritize testing targets. Identify knowledge gaps requiring additional mapping.

### 5.2 Common Pitfalls and Avoidance

**Incomplete Coverage:**

The most common mapping failure is assuming automated tools found everything. Always supplement automated spidering with manual browsing. Test from multiple authentication contexts. Verify that API endpoints and JavaScript-generated content are fully captured.

**False Assumptions:**

Avoid assuming that unlinked content is inaccessible. Don't trust client-side controls to limit server functionality. Never assume that administrative interfaces are properly protected. Question whether identified technologies are accurately fingerprinted.

**Premature Depth:**

Resist the urge to begin active testing before mapping completes. Early testing alerts defenders and may lock accounts. Incomplete mapping causes missed vulnerabilities. Document thoroughly before exploiting.
